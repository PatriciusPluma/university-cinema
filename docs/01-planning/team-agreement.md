# Рабочее соглашение команды кинотеатра

**Участники:** Дмитрий и Марина. **Методология:** Kanban. **Источник состояния задач:** GitHub Issues и связанная с ними доска GitHub Project в отдельном репозитории учебного проекта. Это соглашение задаёт планируемые правила работы. Порядок движения задач, WIP-лимиты и критерии готовности определены в [описании процесса](process.md).

## Ритм и связь

- Короткая синхронизация по понедельникам и четвергам в 19:00, до 15 минут. Обсуждаем завершённое, следующую задачу, блокировки и очередь ревью. Если участник не может присутствовать, он заранее оставляет обновление в переписке.
- Для быстрых сообщений и созвонов используем Telegram. Решения, меняющие требования, приоритет, оценку или технический подход, записываем в соответствующей GitHub Issue; договорённость в мессенджере сама по себе не заменяет запись в трекере.
- В рабочие дни отвечаем на обычные сообщения в течение **одного рабочего дня**. Блокировку, мешающую продолжать работу, помечаем `blocked` в Issue и отправляем партнёру ссылку на неё сразу после обнаружения.
- Раз в неделю на синхронизации проверяем приоритет трёх ближайших готовых историй и фактические показатели потока. Задачи перемещаем по доске при реальном изменении состояния, не задним числом перед встречей.

## Выполнение задач и ревью

- Одновременно у каждого участника не более одной основной истории в колонке «В работе». Перед началом следующей истории сначала помогаем закрыть карточку в «Ревью» или устранить блокировку, если достигнут WIP-лимит.
- На каждую историю назначаем одного исполнителя, второй участник проверяет результат. Разделение конкретных историй фиксируем в Issues при планировании работы; назначение в таблице ниже не закрепляет за человеком весь набор продуктовых функций.
- Каждое изменение кода выполняем в отдельной ветке и через pull request, связанный с Issue. В описании pull request указываем `Closes #N`, краткое изменение, выполненные проверки и связь с критериями приёмки. Большое изменение разбиваем на самостоятельные части, которые можно проверить без чтения несвязанных изменений. Если после слияния развёртывание не прошло, Issue возвращаем в работу до восстановления.
- Автор запрашивает ревью только после самостоятельной проверки и запуска доступных обязательных тестов. Партнёр отвечает на запрос **в течение одного рабочего дня**. Автор не одобряет собственный pull request. Слияние выполняем после одобрения партнёра и успешного CI; продуктовая Issue закрывается после выполнения Definition of Done, включая применимое развёртывание.
- Замечания ревью обсуждаем в pull request. Сначала сверяемся с критериями приёмки и наблюдаемым поведением. Если согласия нет, проводим созвон до 15 минут; при необходимости проверяем спорный вариант небольшим тестом. Если оба варианта приемлемы и данных недостаточно, выбираем более простой для последующего изменения, записываем решение и причину в Issue. Повторяющийся спор выносим на ближайшую синхронизацию и уточняем правило команды.

## Ответственность

| Область процесса | Основной ответственный | Проверяет и подменяет |
|---|---|---|
| Актуальность бэклога, зависимости и приоритеты | Дмитрий | Марина |
| Критерии приёмки и проверка пользовательских сценариев | Марина | Дмитрий |
| Настройка и исправность CI/CD | Дмитрий | Марина |
| Автоматические тесты и контроль качества | Марина | Дмитрий |
| Доска, WIP и метрики потока | Марина | Дмитрий |
| План релиза и пересчёт оценок | Дмитрий | Марина |

Основной ответственный поддерживает соответствующую область процесса; это не исключает вклад второго участника. Продуктовые истории распределяются отдельно по готовности, загрузке и компетенциям. Изменение ответственности согласуем вместе и фиксируем в этом документе.
