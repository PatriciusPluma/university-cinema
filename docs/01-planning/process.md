# Процесс разработки команды

## Выбор методологии

Для команды из двух человек выбран **Kanban**. Работа ведётся непрерывным потоком: следующая подготовленная история берётся после освобождения места в работе. Источником задач служит [бэклог пользовательских историй](backlog.md); приоритеты и состав релиза определены в [плане MVP](prioritization.md).

| Фактор выбора процесса | Условия проекта                                                                    | Решение |
|---|------------------------------------------------------------------------------------|---|
| Размер команды | Два участника разрабатывают и проверяют работу друг друга.                         | Короткая синхронизация и явные ограничения незавершённой работы полезнее отдельных ролей и церемоний Scrum. |
| Изменчивость требований | В ходе работы будут уточняться интеграция оплаты, защита мест и критерии качества. | Очередь можно переприоритизировать по мере появления данных, не дожидаясь конца спринта. |
| Зависимости и риск | Истории покупки связаны: сеанс → места → заказ → оплата → билет.                   | Визуализация блокировок и вытягивание готовых историй помогают не накапливать начатые, но незавершённые задачи. |
| Характер поставки | Изменения проходят через Issue, pull request, ревью, CI и развёртывание.           | Колонки отражают фактическое состояние каждой истории; завершение фиксируется после выполнения Definition of Done. |

## Доска GitHub

**GitHub Issues** используются как карточки задач. В связанном **GitHub Project** планируется представление *Board* с полем `Status` и следующими значениями:

| Колонка `Status` | Когда задача находится здесь | Лимит |
|---|---|---:|
| Бэклог | История записана, но ещё не прошла Definition of Ready или не выбрана для ближайшей работы. | Без лимита |
| Готово к работе | История прошла Definition of Ready, зависимости сняты, приоритет подтверждён. | Не более 3 |
| В работе | Назначен исполнитель и начата реализация или подготовка изменения. | Не более 2 |
| Ревью | Открыт pull request, автор считает изменение готовым к проверке партнёром. | Не более 1 |
| Готово | Выполнены все условия Definition of Done; Issue закрыта. | Без лимита |

## Обоснование WIP-лимитов законом Литтла

Закон Литтла для устойчивого потока: **L = λ × W**, где L — среднее число задач в системе, λ — средняя пропускная способность, W — среднее время прохождения. До появления фактических данных используется та же условная скорость, что в [прогнозе Монте-Карло](./release-plan.md): **2,5 завершённые истории в неделю**. Это плановое допущение, а не измеренная скорость команды.

Для первоначального планирования команда задаёт ориентиры среднего времени по этапам и при скорости 2,5 истории в неделю рассчитывает соответствующий средний WIP по формуле **L = λ × W**:

| Статус | Плановое среднее время на этапе | Расчёт среднего WIP | Стартовый лимит |
|---|---:|---:|---:|
| Готово к работе | 1,2 недели | 2,5 × 1,2 = 3 задачи | 3 |
| В работе | 0,8 недели | 2,5 × 0,8 = 2 задачи | 2 |
| Ревью | 0,4 недели | 2,5 × 0,4 = 1 задача | 1 |


## Definition of Ready

История переводится в «Готово к работе», когда выполнены все условия:

1. Указаны пользователь, действие и ценность в формулировке «Как …, я хочу …, чтобы …»; результат помещается в одну проверяемую историю.
2. Есть не менее двух проверяемых критериев приёмки в формате «Дано / Когда / Тогда», включая существенные ошибочные случаи для оплаты, мест и статусов.
3. Указаны итоговая оценка SP, приоритет, необходимые зависимости и ссылка на связанные истории; незавершённая зависимость не блокирует начало этой работы.
4. Понятны данные или доступы, необходимые для реализации и проверки; открытые вопросы либо закрыты, либо вынесены в отдельную задачу с решением о том, что входит в историю.
5. Другой участник подтвердил, что историю можно взять в работу без дополнительного уточнения результата.

## Definition of Done

История переводится в «Готово», когда выполнены все применимые условия:

1. Реализованы критерии приёмки; результат проверен на целевом пользовательском сценарии и в предусмотренных ошибочных случаях.
2. Добавлены или обновлены уместные автоматические тесты. Для удержания мест и оплаты проверены конкурентные, повторные и неуспешные запросы, если они относятся к истории.
3. Документация и описание API обновлены, если поведение или способ запуска изменились.
4. Изменение привязано к Issue, прошло pull request и ревью вторым участником; замечания устранены либо их решение зафиксировано.
5. Обязательные проверки CI прошли успешно; изменение слито в основную ветку.
6. Для продуктового изменения проверено развёртывание в согласованной среде и доступность результата. Для документационной задачи достаточно публикации в основной ветке.
7. В Issue оставлена ссылка на pull request и свидетельство проверки критериев; Issue закрыта после выполнения предыдущих пунктов.
